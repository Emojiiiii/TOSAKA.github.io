## 开发时间线

### 2026.10.08｜网站基础搭建与视觉设计

**开发目标**

建立网站的基础结构，确定整体视觉方向，并实现桌面端与移动端的基本适配。

**实现过程**

**1. 网站基础架构**

- 使用 HTML、CSS 和 JavaScript 搭建网站。
- 通过 GitHub Pages 部署，使网站能够公开访问。
- 规划 Home、Portfolio、Journal、About 和 Contact 等主要模块。
- 将页面样式与结构分离，为后续添加功能和维护代码做准备。

**2. 视觉风格设计**

网站主要面向游戏行业相关岗位，因此我希望在视觉上保留一定的游戏科技感，但又不让复杂的装饰影响作品本身的展示。

最终选择以深色背景、简洁排版和较大留白为基础，通过背景图、字体层级及页面动画增加视觉表现力。

**3. 响应式背景设计**

首页最初采用单张背景图片，但在测试中发现，适合电脑横屏的图片并不一定适合手机竖屏。

为了解决这一问题，开始采用根据屏幕比例切换不同背景图片的方案，使桌面端与移动端能够分别使用更适合的构图。

**4. 页面交互设计**

为了避免作品集变成普通的长页面滚动展示，尝试引入页面切换动画与视差效果，让不同内容区块之间的过渡更加自然。

同时重新考虑 Contact 模块的交互方式：相比将联系方式直接放在页面底部，我更倾向于让访问者通过导航栏主动打开联系方式，使主要浏览流程集中在作品与个人介绍上。

**遇到的问题与解决思路**

开发过程中发现，桌面端与移动端不仅存在屏幕尺寸差异，在滚动行为和触摸交互上也有所不同。

例如，移动端测试中曾出现页面打开后自动跳转到下方区域的问题，需要进一步检查页面初始化、滚动位置与动画逻辑之间的关系。

**阶段成果**

完成网站的基础页面结构、初步视觉风格、背景适配方案，以及页面切换交互的基础开发。

### 2026.10.08｜Journal 内容管理系统搭建

**开发目标**

建立一个可以长期维护的文章系统，用于发布设计过程、项目总结及技术开发记录，而不需要每新增一篇文章就手动制作独立 HTML 页面。

**实现过程**

**1. 引入内容管理系统**

- 将 Pages CMS 与 GitHub 仓库连接。
- 使用 Markdown 作为文章内容格式。
- 配置 `.pages.yml`，定义文章管理方式及媒体文件路径。
- 建立 Journal 文章存储目录。

**2. 实现动态文章列表**

最初完成 CMS 配置后，文章虽然能够生成独立页面，但 Journal 首页不能自动显示新的文章。

因此进一步完善文章列表的读取与生成逻辑，使新发布的内容能够出现在 Journal 首页。

**3. 处理文章访问问题**

在测试过程中，还遇到了文章已经发布但无法正常显示，以及部分页面返回 404 的情况。

通过检查文章存储位置、发布状态、访问路径与生成文件之间的关系，逐步调整系统配置。

最终完成文章列表和文章详情页的访问测试，并清理部分不再需要的文件。

**遇到的问题与解决思路**

这次开发中最大的挑战不是文章页面本身的视觉设计，而是理解内容、路径和页面生成机制之间的关系。

之前的网站主要依靠手动编写页面，而 CMS 的加入让内容管理与页面布局逐渐分离。

这种结构使后续发布内容更加方便，同时也减少了重复修改 HTML 的需求。

**阶段成果**

完成 Journal 的基本内容管理与文章发布流程，可以通过 CMS 创建文章，并通过网站访问相应的内容。

**开发反思**

相比单纯增加页面，建立可复用的内容管理机制更有长期价值。

### 2026.10.09｜统一视觉规范与 Portfolio 详情页开发

**开发目标**

改善网站不同页面之间的视觉一致性，同时为 Portfolio 的作品卡片增加独立详情页，让未来的游戏设计项目能够拥有更完整的展示空间。

**实现过程**

**1. 统一字体和导航设计**

在测试中发现，不同页面的字体风格、字号以及顶部导航栏的尺寸存在差异。

因此对现有页面进行了视觉规范调整，使它们在字体和导航布局方面尽可能保持统一。

**2. 实现 Portfolio 详情页**

- 为首页三个 Portfolio 作品卡片增加点击打开功能。
- 复用此前 Journal 已经实现的文章详情页结构。
- 调整 Portfolio 详情页导航，使其与 Journal 保持一致。
- 对页面打开及导航功能进行测试。

**3. 考虑后续内容扩展**

与 Journal 主要展示图文内容不同，Portfolio 需要展示游戏项目中的多种素材，例如武器设计图、不同角度的展示图片、动画视频，以及部分技术实现内容。

因此，后续需要对作品编辑与媒体展示结构进行扩展，而不只是简单复用文章正文。

**遇到的问题与解决思路**

最初可以为 Portfolio 重新制作一套独立的详情页系统，但这样会增加重复代码，后续修改导航、排版或交互时，也可能需要同时维护多套结构。

因此，我优先选择复用已经完成的 Journal 功能，再针对 Portfolio 的特殊内容需求逐步扩展。

这种方式有助于降低开发和维护成本，也更符合整个网站长期迭代的需求。

### 2026.10.10｜Portfolio 多媒体管理与动态封面设计

**开发目标**

进一步完善 Portfolio 作品展示系统，使其能够承载游戏设计项目中的多种媒体内容，同时改善首页作品卡片的视觉表现。

**实现过程**

**1. 扩展 Portfolio 内容管理结构**

- 完成多媒体内容管理相关配置的部署。
- 为作品详情页支持多张图片、视频及代码内容规划相应的数据结构。
- 建立测试作品，用于后续验证不同媒体类型的上传与展示效果。
- 继续沿用已有 CMS 和详情页结构，减少重复开发。

**2. 设计首页动态封面功能**

原有 Portfolio 卡片采用静态封面，无法充分展示同一分类下的多个作品。

因此，设计了自动读取对应分类文章封面，并在首页卡片内进行轮播的功能方案。

交互上保留原有导航逻辑：卡片点击后仍进入对应作品分类页面，而不是直接打开某一篇文章。

**3. 规划模块化实现方式**

为避免首页 HTML 文件持续膨胀，将封面读取、视觉样式和轮播逻辑分别规划到独立文件中：

- `_includes/portfolio-cover.html`：封面内容生成。
- `css/portfolio-cards.css`：卡片视觉样式。
- `js/portfolio-slideshow.js`：自动轮播逻辑。

目前动态封面功能已完成实现方案整理，尚未部署到线上网站。

**遇到的问题与解决思路**

Portfolio 与 Journal 虽然可以共享页面结构，但两者对内容展示的需求存在明显区别。

例如，Portfolio 需要更丰富的图像与视频展示能力，而首页卡片则需要自动获取相应作品的信息。

因此，决定在保留现有内容管理架构的基础上进行扩展，尽量减少模块间不必要的依赖。

另外，目前 Weapons 分类仅有一篇带封面的 BY15 作品，暂时无法体现多张封面自动轮播的最终效果，需要在后续增加更多作品进行验证。

**阶段成果**

- 完成 Portfolio 多媒体管理相关配置部署。
- 创建未发布的测试作品。
- 明确首页动态封面的交互逻辑与模块化实现方案。

### 2026.10.10｜Journal 文章排版问题排查

**开发目标**

改善 Journal 文章的内容展示效果，解决 Description 文本换行及 Markdown 表格显示异常的问题。

**实现过程**

**1. 排查 Description 换行问题**

测试时发现，在编辑器中输入的多行 Description 内容，显示到网站后没有按照原有格式换行。

通过检查文章详情页模板，发现现有 HTML 已经能够输出 Description 内容，因此优先从 CSS 文本排版规则寻找原因。

计划通过 `white-space: pre-line` 保留文本中的换行，而不修改原有 HTML 结构。

**2. 排查 Markdown 表格样式**

在文章中尝试使用 Markdown 表格时，发现页面没有按照预期展示表格效果。

因此检查文章正文的渲染方式，并计划补充表格相关的 CSS 样式，使表格具有更清晰的边框、间距及阅读层级。

**3. 减少不必要的结构修改**

对于已有功能，优先判断问题属于内容、样式还是页面结构，再选择修改范围。

避免为了修复简单的视觉问题而直接重写 HTML 模板。

**遇到的问题与解决思路**

网站开发初期，页面结构和视觉表现通常可以同时调整。但随着 Journal、Portfolio 等多个模块开始复用已有模板，修改公共结构可能影响其他页面。

因此，这次排查采用尽量缩小修改范围的思路，将文本排版问题优先交给 CSS 处理。

**阶段成果**

- 明确 Description 换行的 CSS 调整方案。
- 整理 Markdown 表格的显示优化方向。
- 保留原有文章 HTML 结构。

### 2026.10.12｜Journal 与 Portfolio 页面排版重构

**开发目标**

随着网站内容不断增加，原有 Journal 和 Portfolio 详情页的居中单栏布局逐渐暴露出一些问题。

尤其是在桌面端全屏浏览时，大量内容集中在页面中央，两侧空间利用率较低，文章的视觉层级与信息组织也不够清晰。

因此，本次开发希望在保留网站原有视觉风格的基础上，引入更适合长篇内容阅读的排版系统，同时改善桌面端与移动端的浏览体验。

**实现过程**

**1. 探索新的页面排版方式**

参考骨骼型排版（Skeleton Layout）与编辑式排版（Editorial Layout）的设计思路，重新规划文章页面的信息结构。

- 将原有居中单栏布局调整为左右分区的双栏方案。
- 左侧用于文章目录及快速导航，右侧作为主要阅读区域。
- 扩大桌面端的内容展示宽度，提高屏幕空间利用率。
- 重新规划标题、正文及章节之间的间距与层级，使长篇文章更加易读。

**2. 统一 Journal 与 Portfolio 的排版规范**

考虑到 Journal 和 Portfolio 已经具有一定程度的页面结构复用，本次调整不再针对单个页面分别设计，而是尝试建立一套共用的排版样式。

通过独立的 `editorial-layout.css` 管理相关布局，减少重复样式，方便未来对不同类型的文章进行统一调整。

同时为 Journal、Work 分类页面及作品详情页规划对应的样式接入方式。

**3. 优化开发日志的时间线导航**

针对持续更新的开发日志，普通文章目录无法满足按时间查找记录的需求。

因此进一步提出日期索引的设计方案：

- 左侧导航显示完整的开发日期。
- 每个日期对应右侧的一条开发记录。
- 点击日期可直接跳转到对应内容。
- 通过导航高亮帮助读者识别当前阅读位置。

该功能的目标是让开发日志不仅能够顺序阅读，也能够作为可检索的项目开发档案使用。

**4. 响应式布局适配**

针对不同屏幕宽度制作了布局测试方案，分别检查手机端、常规桌面端及宽屏显示环境下的排版表现。

重点关注双栏布局在小屏幕下的适配，以及目录导航是否会影响正文阅读。

**遇到的问题与解决思路**

本次开发中出现的主要问题是，新排版方案准备完成后，网站实际显示效果没有发生预期变化。

排查方向集中在新样式文件是否正确接入、页面是否加载对应 CSS，以及修改是否成功提交部署。

此外，GitHub 写入操作曾出现权限错误，导致部分修改无法直接同步至线上网站。

因此，本次工作将布局方案设计与实际部署验证分开处理，避免把本地完成的设计直接视为线上功能已经实现。

**阶段成果**

- 完成双栏编辑式排版的设计方案。
- 制作响应式布局文件，并进行不同屏幕宽度的示例测试。
- 明确 Journal 与 Portfolio 共享排版样式的实现方向。
- 确定开发日志采用完整日期索引的导航方案。

### 2026.10.16｜TOSAKA Q&A：匿名问答系统设计与后端搭建

**开发目标**

为个人作品集网站增加独立的问答功能，让访问者能够直接向我提出有关作品、设计思路或技术实现的问题。

考虑到作品集主要面向招聘人员、游戏工作室及其他访问者，我希望尽可能降低互动门槛，让用户无需注册账号或登录即可匿名提问。

同时，为避免垃圾信息、不适当内容及恶意提交直接出现在公开网站上，决定采用「匿名提交、后台审核、人工回答、公开展示」的交互流程。

**实现过程**

**1. 确定问答系统的整体架构**

为了保留现有 GitHub Pages 的静态网站架构，同时增加数据存储和后端处理能力，选择使用 Cloudflare 提供的服务。

主要技术包括：

- GitHub Pages：继续承担网站前端的部署与访问。
- Cloudflare Workers：处理问答系统的 API 请求。
- Cloudflare D1：保存访问者提交的问题及其审核状态。
- Cloudflare Turnstile：对匿名提交进行人机验证，降低自动化垃圾请求风险。

通过这种方式，不需要将整个作品集迁移到新的服务器，也能为静态网站增加动态交互能力。

**2. 建立数据库与后端 API**

创建 D1 数据库 `tosaka-qa`，并建立用于保存问答信息的 `questions` 数据表。

随后部署 Cloudflare Worker：

`tosaka-qa-api`

由 Worker 统一处理前端提交、数据验证与数据库写入。

在数据结构设计上，为问题保留审核状态，使新提交的内容不会立即向公众开放。

**3. 实现匿名问题提交**

在网站前端接入匿名提问功能，并与 Worker API 建立通信。

访问者可以直接填写问题，通过 Turnstile 验证后将内容提交至后端。

提交成功的问题会保存到 D1 数据库，并保持待审核状态。

**4. 规划后台审核机制**

考虑到问答内容需要由我本人筛选和回复，因此规划独立的管理系统：

`TOSAKA Q&A Manager`

管理后台与公开问答页面分离，只有管理员能够查看尚未公开的问题、编辑回复以及决定是否发布。

**遇到的问题与解决思路**

**问题一：静态网站如何实现动态问答？**

GitHub Pages 本身不提供可以直接写入的后端数据库。

如果将问题直接写入网站文件，不仅需要额外的授权机制，也不适合处理大量匿名请求。

因此采用 Cloudflare Workers 与 D1 作为独立后端，使网站展示层与数据处理层分离。

**问题二：如何同时实现匿名提问和内容安全？**

匿名功能能够降低访问者的使用门槛，但也会增加垃圾信息和恶意提交的风险。

对此采用两层处理机制：

- 提交阶段使用 Turnstile 进行人机验证。
- 展示阶段采用后台审核，只有明确发布的内容才会公开。

这样既保留匿名互动的便利性，也能控制公开内容的质量。

**阶段成果**

- 确定问答系统的前后端架构。
- 创建 Cloudflare D1 数据库。
- 部署 `tosaka-qa-api` Worker。
- 接入 Turnstile 人机验证。
- 完成匿名提问及 D1 数据写入测试。
- 验证新问题能够以待审核状态保存，不会自动公开。

### 2026.10.17｜TOSAKA Q&A：后台管理、问答发布与安全机制完善

**开发目标**

在匿名提交与数据存储功能已经建立的基础上，完善问答系统的管理流程，使访问者提交的问题能够由管理员统一查看、回答和发布。

同时解决后台访问权限、密码验证及公开问答页面的显示问题，让整个系统形成完整的使用流程。

**实现过程**

**1. 开发独立后台管理系统**

建立 `TOSAKA Q&A Manager`，将后台管理功能与公开网站分离。

后台主要负责：

- 查看数据库中收到的提问。
- 区分待审核、已发布及忽略的问题。
- 为问题编写和保存回答。
- 控制问答内容是否公开。
- 管理员退出登录。

相比让用户提交的问题直接显示在前端，这种方式提供了更完整的内容审核流程。

**2. 实现管理员身份验证**

由于后台涉及修改和发布问答内容，不能直接向所有访问者开放。

因此增加受保护的管理员登录机制，并结合 Cloudflare Worker 环境中的密钥配置管理认证信息。

相关安全设计包括：

- 使用 Worker Secrets 保存管理员密码和会话密钥。
- 通过 Session Cookie 维持管理员登录状态。
- 加入登录失败频率限制。
- 为后台管理操作加入 CSRF 防护。
- 设置安全响应头，降低部分常见 Web 攻击风险。

这些措施的目标不是建立复杂的用户系统，而是为单人管理的网站提供合理的访问保护。

**3. 完成问答审核与公开展示**

将后台管理操作与 D1 数据库中的问题记录关联。

管理员能够为待审核问题填写回答，并将其状态修改为 `published`。

公开网站则通过独立的 API 读取已发布问答，不向普通访问者提供未审核的问题内容。

在测试过程中，成功将测试问题发布至数据库，并验证公开 API 能够读取已发布的数据。

这使问答系统形成了完整流程：

匿名提交 → 数据库存储 → 管理员审核 → 编写回复 → 公开展示。

**4. 修复后台配置与登录问题**

开发和测试过程中，曾出现后台显示 `Admin service not configured` 的情况。

问题出现在调整管理员密码及相关配置之后。

通过检查 Worker 的认证配置、密钥设置与登录逻辑，逐步排查问题，并最终恢复后台登录功能。

同时对管理员密码规则进行调整，使认证方式更适合个人管理场景。

**5. 优化公开问答页面**

在前端接入公开问答列表后，发现页面出现重复分隔线以及不必要的空白区域。

排查发现问题与重复的问答容器及旧版空状态结构有关。

因此调整页面标记结构，清理重复元素，使问答内容能够按照预期排版展示。

**6. 规划新问题邮件提醒**

由于管理员不会持续打开后台检查新问题，因此提出通过 Outlook 电子邮件接收自动提醒的需求。

考虑到使用个人 Microsoft 账号时，部分 Microsoft 身份验证与组织租户机制存在兼容性限制，对不同的邮件通知实现方案进行了评估。

目前邮件提醒仍处于方案研究与配置阶段，尚未完成可用性验证。

**遇到的问题与解决思路**

**问题一：怎样确保后台只有管理员能够访问？**

由于问答系统允许任何访问者匿名提交内容，公开接口与管理员接口必须具备不同的权限。

因此将管理员身份验证、会话管理和后台管理操作进行独立处理，同时通过环境密钥减少敏感配置直接写入源代码的风险。

**问题二：怎样避免尚未审核的问题被公开？**

即使前端隐藏待审核的问题，如果公开 API 返回了完整数据库内容，仍然可能造成信息泄露。

因此将筛选逻辑放在后端，由公开 API 仅返回状态为 `published` 的问答记录。

**问题三：如何定位后台配置故障？**

在修改密码后出现配置错误时，不能仅凭页面提示判断问题来自密码本身。

需要分别检查 Worker Secrets、后端配置和登录逻辑，确认各部分能否正常配合。

这次排查也体现了动态网站与静态页面的区别：有些问题无法单纯通过浏览器前端代码判断，还需要检查服务端的运行配置。

### 2026.10.18–10.19｜Q&A 邮件通知系统与后台管理优化

**开发目标**

此前已经完成 TOSAKA 匿名问答系统的基础功能，包括匿名提交、数据库存储、管理员登录以及回答发布。

但是在实际使用过程中发现，管理员需要主动打开后台才能知道是否收到了新问题。

考虑到网站主要作为个人作品集使用，访问者提交问题的频率可能并不固定，因此希望建立自动邮件通知机制，使新问题能够及时被发现和处理。

与此同时，进一步完善后台的问题管理操作，明确「忽略」与「永久删除」之间的区别。

**实现过程**

**1. 研究邮件通知服务的实现方式**

最初考虑通过 Microsoft Azure 与 Outlook 邮箱建立邮件通知服务。

但在实际配置过程中，遇到了 Microsoft 应用注册与身份验证方面的问题。

此外，Azure 注册需要提供支付卡信息，而部分学生订阅还存在使用期限限制。

考虑到网站预计需要长期维护，因此重新评估邮件服务方案，优先选择部署成本较低、维护相对简单的实现方式。

**2. 部署独立的邮件通知服务**

转向使用 Google 提供的 Web 应用部署方式，通过独立服务处理邮件通知请求。

整体通知流程设计为：

访问者提交问题 → Cloudflare Worker 接收请求 → D1 数据库存储 → 通知服务处理 → 向管理员邮箱发送提醒。

这种结构可以保留原有的 Cloudflare 问答系统，同时将邮件发送逻辑独立出来。

在配置过程中，完成 Web 应用部署，并引入 `NOTIFY_TOKEN` 作为通知请求的身份验证凭据。

通过令牌校验，避免通知接口完全开放给未经授权的请求。

**3. 进行通知服务配置与测试**

完成通知服务的基础部署后，进一步检查 Web 应用与 Cloudflare Worker 之间的配置关系。

重点包括：

- 确认通知服务地址与请求方式。
- 配置双方使用的 `NOTIFY_TOKEN`。
- 检查令牌是否一致。
- 测试服务调用是否能够成功完成。

经过配置调整，通知流程完成了初步联通测试。

**4. 重新梳理管理员问题管理逻辑**

在使用 Q&A Manager 时，进一步考虑已处理问题应如何管理。

原有后台提供「忽略」功能，但忽略问题并不一定意味着从数据库永久删除记录。

因此，将两类操作明确区分：

- **忽略（Ignore）：** 将问题标记为不再处理，保留相关记录。
- **永久删除（Delete）：** 从数据库删除对应问题，通常无法通过后台直接恢复。

在此基础上，提出新增独立的「永久删除」按钮，同时保留已有的「忽略」功能。

为了防止误操作，永久删除还需要增加二次确认步骤。

这一部分已明确功能需求与交互方案，删除操作的实际部署及测试仍需进一步确认。

**遇到的问题与解决思路**

**问题一：如何选择适合长期维护的通知服务？**

个人作品集的访问规模相对有限，不需要过于复杂的企业级邮件系统。

但服务的长期可用性、费用及维护成本十分重要。

因此，没有继续依赖需要额外支付信息或存在期限限制的方案，而是重新选择更适合个人网站的服务架构。

**问题二：如何保护通知接口？**

如果邮件通知接口允许任何人直接调用，可能遭到滥用，造成无意义的邮件发送。

因此增加独立的通知令牌，并要求调用方提供正确凭据。

同时，敏感令牌应当保存在服务端配置中，而不是直接暴露在网站前端 JavaScript 中。

**问题三：如何避免管理员误删数据？**

问答系统中的「忽略」和「删除」代表不同的数据处理行为。

如果两者混用，可能导致本来只想隐藏的问题被永久删除。

因此决定将操作名称、处理逻辑和确认流程分开设计，让管理员能够明确理解每次操作的结果。

- 完成通知服务初步联通测试。
- 明确「忽略」与「永久删除」的不同用途。
- 制定带二次确认的永久删除功能方案。
