## 01 / 项目概述

[MZK_BOT](https://github.com/Emojiiiii/MZK_BOT) 是我过去开发的一个基于 Discord 平台的 AI Bot 项目。

由于项目长期缺乏维护，部分代码依赖的第三方 API、Python 库及相关运行环境已经发生变化，导致原有程序目前无法正常运行。

此次重制并不只是希望让旧代码重新运行，而是借此机会重新审视项目结构，整理历史遗留问题，并逐步改善代码的可维护性与部署方式。

考虑到旧项目可能包含不再使用的依赖、大型模型文件以及历史配置文件，重制的第一阶段没有直接修改 Bot 的主要功能，而是优先处理源代码归档、Git 仓库清理与敏感信息保护。

本文将持续记录 MZK_BOT 从旧项目整理、功能修复到后续重构的完整过程。

## 02 / 开发时间线

### 2026.10.13｜重制启动：旧项目归档与 Git 仓库清理

**开发目标**

为 MZK_BOT 重制建立一个安全、可维护的开发基础。

由于原项目包含长期积累的历史文件，且当前版本已经无法正常运行，因此本次工作的重点是完整保留旧项目的同时，清理不适合继续追踪或公开发布的文件，为后续代码修复做好准备。

**实现过程**

**1. 评估旧项目现状**

首先确认原项目当前的运行状态，并整理后续可能需要处理的技术问题。

主要包括：

- 旧版 OpenAI API 与现有接口的兼容性。
- Discord Bot 相关库和接口的变化。
- Python 依赖与运行环境的兼容性。
- 原有 AI 模型及相关文件的加载方式。
- Git 仓库中可能存在的敏感配置与大型文件。

由于目前尚未完成运行环境和依赖检查，因此暂时不直接判断所有功能失效的具体原因。

**2. 创建完整项目备份**

在正式清理仓库之前，优先保存原项目的完整 Git 历史。

使用 Git Bundle 创建独立备份文件：

`MZK_BOT-before-cleanup.bundle`

备份文件大小约为 460 MB。

随后通过 `git bundle verify` 检查备份完整性，确认备份可以被 Git 正常识别。

在此基础上，建立独立清理副本：

`MZK_BOT_PUBLIC_CLEAN`

后续仓库清理操作优先在该副本中进行，避免直接修改原始项目。

**3. 清理 Git 历史中的敏感配置文件**

在准备公开项目源码时，需要考虑 Git 的历史记录机制。

即使将 `.env` 等配置文件从当前目录删除，过去提交的版本仍然可能保存在 Git 历史中。

因此，采用 `git-filter-repo` 对独立副本进行历史清理。

主要操作包括：

- 下载并验证 `git-filter-repo` 工具。
- 针对历史中的 `.env` 及子目录下的同名文件进行清理。
- 检查这些配置文件是否仍存在于 Git 历史中。
- 保留原始仓库备份，避免破坏不可恢复的历史信息。

完成相应操作后，两项针对 `.env` 文件的检查均未发现匹配结果。

**4. 整理 .gitignore 文件**

检查仓库时发现，原有忽略规则保存在 `gitignore.txt` 中，而不是 Git 默认识别的 `.gitignore` 文件。

因此，将其调整为正确名称，并完善忽略规则。

本次重点整理的文件类型包括：

- `.env` 及相关环境配置文件。
- Python 缓存和虚拟环境。
- 本地生成的压缩文件。
- PyTorch 模型权重文件（如 `.pth`）。
- 部分不适合纳入源码管理的大型模型目录。

同时考虑保留 `.env.example` 作为未来展示配置结构的示例文件。

这一步的目标是减少临时文件、敏感配置及大型运行资源再次被误提交的风险。

**5. 整理大型文件清理方案**

旧项目的历史备份体积较大，说明仓库可能长期追踪了部分不适合存放在 Git 历史中的大型文件。

因此，在历史清理流程中引入 95 MB 的文件大小阈值，并使用 `git-filter-repo` 的大文件处理能力。

相关清理操作已开展，但针对历史中大型文件的全面扫描、结果核验及最终发布尚未完成。

后续需要进一步确认仓库大小、历史文件分布以及清理后的完整性。

**遇到的问题与解决思路**

**问题一：如何在清理旧项目时避免丢失历史代码？**

Git 历史重写可能导致部分旧提交发生变化，如果直接在原始仓库操作，可能增加恢复难度。

因此，选择先创建完整 Bundle 备份，再从备份建立独立清理副本。

这种处理方式将原始项目归档与新版本整理分开，降低了直接破坏原项目的风险。

**问题二：为什么删除敏感文件后，还需要清理 Git 历史？**

Git 不仅保存当前版本，还保留之前提交的文件内容。

因此，普通删除操作无法保证历史中的敏感配置消失。

为解决这一问题，采用专门的 Git 历史过滤工具，并通过清理后的检查结果验证处理情况。

需要注意，历史清理不等于旧密钥自动失效。如有真实凭据曾经进入仓库，仍需要撤销或轮换。

**问题三：如何避免大型模型文件影响仓库维护？**

部分 AI 模型文件体积较大，并不适合与源代码一起进行普通版本管理。

因此，开始将模型资源与核心源码进行区分，利用 `.gitignore` 和历史文件清理减少不必要的仓库负担。

至于后续模型文件的存储与分发方式，将在功能重制阶段进一步确定。

**阶段成果**

- 完成原项目 Git 历史的独立备份及完整性验证。
- 建立 `MZK_BOT_PUBLIC_CLEAN` 清理副本。
- 使用 `git-filter-repo` 处理历史敏感配置文件。
- 完成两项 `.env` 历史检查，未发现匹配结果。
- 修正 `.gitignore` 文件名称并补充忽略规则。
- 开展大型历史文件清理，明确后续核验工作。

目前 MZK_BOT 仍处于不可运行状态，Bot 的功能修复与兼容性改造尚未正式完成。

**开发反思**

这次重制让我重新认识到，软件项目的可维护性不仅取决于程序功能本身，还涉及版本管理、文件组织、数据安全以及长期依赖管理。

过去开发项目时，注意力往往更多集中在功能能否实现，而忽略了仓库中哪些内容应该被追踪、哪些配置需要与源码隔离。

这次没有选择直接重写 Bot，而是优先建立可靠的备份和清理流程。

对于一个长期停止维护的项目而言，先确保历史资料可以保存、现有问题能够被定位，再逐步恢复功能，比盲目修改旧代码更加稳妥。

**下一步计划**

- 完成 Git 历史大型文件的全面扫描与验证。
- 检查清理后的仓库状态，准备公开版本。
- 检查并更新 Python 项目依赖。
- 排查 Discord 与 OpenAI API 的兼容性问题。
- 逐步恢复 Bot 的基础连接、消息处理和 AI 功能。
- 建立基础运行测试流程，为后续代码重构做准备。
